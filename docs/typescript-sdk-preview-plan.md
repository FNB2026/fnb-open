## 2. Minimal public capability and exclusions

The proposed runtime has one operation, provisionally named `exchange`: submit
one caller-supplied five-member envelope to one explicitly configured endpoint
with `POST`, and decode its bounded response. No discovery or other route.
The caller supplies `exchange_id` and explicit `validation_contexts`; there is
no auto-ID, role inference, batch splitting, chain repair, or retry.

The envelope keeps exactly `transport_version`, `protocol_release`, `exchange_id`,
`objects`, and `validation_contexts`. Version values are the supported literals.
Transport types model readable object entries with a JSON object payload; typed
domain bindings may be imported as conveniences but must not narrow the wire
payload into a domain-schema `oneOf`. An object such as `{}` or an unknown schema
ID can be readable protocol-invalid material and must reach the receiver as
`200 rejected`, not be relabelled a local schema/conformance failure. Validate
wire grammar and serialization only; do not add an independent domain judge.

Explicitly excluded: login/signup, JWT/session, cookies, account management,
ACL/permission enforcement, IM/WebSocket, subscriptions, CRUD/query/storage,
workers/migrations/ledger/admin, AI inference/generation, object derivation,
invalidation generation, private Alpha compatibility, telemetry, production
deployment, offline conformance certification, and compatibility reports.
`PermissionSnapshot` remains evidence, not authorization. Accepted means only
the receiver's bounded public validation passed; not saved, applied, complete
history, current permission, or successful product operation.

## 3. Result algebra and correlation

Proposed `exchange` returns a Promise of a discriminated result. The names below
are design labels, not implemented exports. Never collapse them to a boolean,
throw all non-2xx responses, or interpret `Response.ok` as acceptance.

| Result kind | Evidence required | What callers may conclude |
| --- | --- | --- |
| `receipt` | HTTP 200; supported JSON media; exact receipt shape; status accepted/rejected; all three correlation fields equal the submitted snapshot | Only the stated protocol verdict, with rejected a normal negative verdict |
| `problem` | HTTP 400/413/415/500; problem JSON media; one recognized type/status/title tuple; correct optional detail type | A supported transport/evaluation failure, never a verdict |
| `failure` | Invalid input/configuration, cancellation, timeout, network/body failure, oversized response, unsupported status/media, invalid JSON/shape/correlation, or unexpected internal SDK error | No reliable verdict; local categories are not protocol Problem Details |

Failure categories are proposed as `invalid-input`, `configuration`, `cancelled`,
`timeout`, `network`, `invalid-response`, `response-limit`, and `internal`.
No raw request/response, object identifier, URL credential, local path, stack,
or server error text is emitted in default diagnostics. Configuration validation
at client creation may throw a typed configuration error before any network;
ordinary exchange outcomes use the result union. Fatal VM/resource termination
is outside the ability of any Promise API to guarantee a result.

For a receipt, require exactly four members, non-empty string versions/ID and
status `accepted` or `rejected`. Compare `transport_version`, `protocol_release`,
and `exchange_id` by exact string equality to an immutable pre-dispatch snapshot:
no trim, case folding, Unicode normalization, reconstruction, or latest-request
global variable. A mismatch for either accepted OR rejected is `invalid-response`.
Each concurrent call owns its correlation state; echo fields are not proof of
receiver authenticity or persistence. Never fabricate a receipt after timeout.

| Problem suffix | HTTP status | Exact title |
| --- | --- | --- |
| `malformed-envelope` | 400 | Malformed exchange envelope |
| `unsupported-media-type` | 415 | Unsupported exchange representation |
| `payload-too-large` | 413 | Exchange payload too large |
| `unsupported-transport-version` | 400 | Unsupported transport version |
| `unsupported-protocol-release` | 400 | Unsupported protocol release |
| `evaluation-failure` | 500 | Exchange evaluation unavailable |

Types use the exact prefix `https://www.fnbapp.net/problems/object-exchange/1.0/`.
Body `status` must be an integer equal to the HTTP status, with the table's type
and title. A receipt on non-200, a problem on 200, unknown type, HTML gateway
error, 204, 201, 401/403/404/429, or malformed known problem is `invalid-response`
(generic observed status may be retained). Do not guess a meaning from text.
Do not fetch a problem URI. Optional detail is untrusted and not logged; expose
it only in the validated structured problem value, never an exception message.

RFC-0004 says consumers ignore unrecognized problem extension members. The
SDK therefore checks the recognized base fields and strips/ignores unknown
problem members after strict parsing, even though OpenAPI's closed problem
schemas constrain what a conforming producer emits. Unknown receipt members
remain errors. This deliberate consumer/emitter distinction must have tests;
do not blindly apply a generated closed emitter schema to the problem consumer.
An extension must still be valid strict JSON; ignoring it does not allow nested
duplicate keys, NaN, invalid UTF-8, or exceeding limits.

## 4. Strict JSON and fail-closed boundaries

Request API accepts JSON data, not raw JSON text. Before sending, reject cycles,
BigInt, nonfinite numbers, undefined, functions, symbols, sparse arrays, getters,
custom `toJSON`/Date/class instances, and values that JSON serialization would
silently omit or coerce. Accept plain records/arrays/scalars only; reject unsafe
integer Numbers. Trusted caller input is required: reflective checks are not a
sandbox against malicious Proxy traps. Never silently redact or repair input.
Take a validated detached snapshot before asynchronous work so mutation during
fetch cannot change correlation. Do not normalize object IDs or content.

No arbitrary-precision JSON/decimal guarantee: normal JavaScript fractional
Number semantics apply to request data. Values already rounded before the call
cannot be recovered. No raw-number token/BigInt/Decimal API in this preview;
consumers requiring lossless arbitrary-precision payloads must not use it.
This limitation does not change the frozen protocol's numeric rules.

Read a response byte stream once, bounded before full allocation; do not use
`response.json()` or decode-with-replacement as the correctness boundary. Decode
with fatal UTF-8, disallow a BOM, and parse one JSON value with duplicate-member
detection at every object depth. Compare decoded member names, so escaped and
literal equivalents collide. Reject NaN/Infinity, trailing data, invalid grammar,
overflowing numeric conversion, and non-object top-level responses. Treat
`__proto__`, `constructor`, and similar keys as data in null-prototype records,
never use them in property-assignment merges. Response numeric fields are only
small statuses; nonrepresentable numbers fail closed, with no precision claim.

Proposed bounded parser: handwritten tokenizer/parser for JSON grammar, with
depth/token/byte caps, no regex-only duplicate detector and no reviver-after-
JSON.parse substitute. It is SDK-local transport machinery, not a schema or
semantic validator. Independent parser review and adversarial tests are a hard
implementation/release gate. If a reviewed parser dependency becomes necessary,
that requires a separate dependency decision; zero dependency is not permission
to ship an unreviewed parser. No parser code is written in this planning PR.

Media type/charset tokens are compared case-insensitively. Accept the matching
`application/json` or `application/problem+json`, with no parameters or only
`charset=utf-8`; wrong/multiple media values or other parameters fail closed.
Absent/identity response encoding is supported; compare identity case-
insensitively, reject non-identity visible encoding. Fetch can transparently
decode content and combine headers: checks cover its observable response, not
raw HTTP framing or a guarantee that hidden duplicate headers can be detected.
Body budgets count bytes delivered by fetch, not compressed wire bytes. No
custom decompression support. Mock interoperability uses unencoded responses.

## 5. Endpoint, runtime, fetch and lifecycle

| Concern | Proposed first-preview decision |
| --- | --- |
| Runtime | Node.js 22 only initially; exact integration job starts from repository pin `22.22.2`; re-evaluate supported/security status before future release |
| Other environments | Browser, React Native, Deno, Bun, edge workers and other Node majors not supported claims; CORS/browser testing is deferred, not a Mock change |
| Module format | ESM runtime plus declaration output; no CommonJS bundle/polyfills in first preview |
| Fetch | Native runtime fetch by default; optional explicitly trusted compatible fetch injection for deterministic tests; no axios/HTTP client dependency |
| Endpoint | Required full absolute `/exchange` URL; no default production host or discovery; reject credentials, query, fragment, non-HTTP schemes and other paths |
| Scheme | HTTPS required except plain HTTP with numeric IPv4 loopback literal 127.0.0.0/8; reject HTTP localhost/DNS names/LAN/public hosts and IPv6 until separately tested |
| Request | POST; fixed Content-Type application/json and Accept for the two JSON response media types; UTF-8 serialized byte body with known length, not streaming/chunked |
| Fetch policy | `redirect: error`, `credentials: omit`, no cookies/auth/custom product headers, no custom TLS bypass/agent; no retry/backoff or automatic batch replay |
| Timeout | Integer milliseconds in 1..60000, proposed default 10000; total deadline across fetch, body read and response validation, not merely until headers |
| Cancellation | Optional caller AbortSignal plus internal deadline controller; no monkeypatching global fetch or AbortController |
| Local caps | Request 1 MiB/256 objects, response 64 KiB, JSON depth 64 and 32768 tokens by default; integer overrides may reduce each cap to at least 1, not exceed the default; not protocol constants |

Pass encoded bytes so Node native fetch can supply Content-Length compatible
with the established Mock. Verify this on real HTTP rather than assume it from
types. Do not add chunked handling or SDK-specific routes to #28.

Validate configuration and input before dispatch. Already-aborted calls do not
send; record first terminal cause per call (caller cancellation or SDK deadline),
and do not classify solely by an exception's name. A network failure without
either abort cause stays network. The deadline remains active while reading;
cancel the reader/abort fetch on limits or cancellation, remove listeners/timers
in finally, and settle exactly once. If cancellation arrives before a validated
result is committed, no late receipt escapes. After settlement, later abort
events do not mutate the result. Timeout/cancel do not prove server-side rollback.

Serialization/parsing are bounded synchronous work, with deadline checkpoints
before and after them; JavaScript timers do not provide hard CPU preemption.
A trusted injected fetch must honor request policy, AbortSignal and bounded
stream behavior. The SDK does not sandbox injected code or promise OS isolation.
Endpoint safety is syntactic policy, not DNS/SSRF protection for arbitrary HTTPS
destinations; the caller must choose a trusted receiver. No real service is
contacted during development. Concurrency tests use a separate response harness
because the established Mock is intentionally serial.

## 6. Generated versus handwritten material

| Material | Source and method | Must not do |
| --- | --- | --- |
| Domain `.d.ts` | Regenerate via existing manifest-driven binding generator; reuse byte-identical declarations, record snapshot/digests | Hand-edit bindings or claim TypeScript proves runtime conformance |
| Envelope/context/receipt declarations and known problem table | New deterministic generator reading locally verified frozen OpenAPI; fail on unsupported keywords; preserve canonical external schema references | Fetch remote refs, inline altered domain schemas, silently flatten conditional types |
| Runtime client, serializer/parser, response guards, correlation and lifecycle | Handwritten thin layer using generated wire metadata; consumer extension rule explicit | Generated generic client behavior that auto-retries, follows redirects, trusts response.json/Response.ok, or drops correlation |
| Tests | Handwritten independent expected outcomes from public worlds/contract, plus test-only fault responses | Use generator output alone as the expected-answer oracle |

The default is narrow extraction/generation, not a generic OpenAPI client
generator with unchecked defaults. No generator/tool dependency is installed
now. Later implementation must add deterministic regenerate/check commands,
type expectation tests and repeat-render byte comparison. Runtime domain
validation remains at the public receiver; client wire guards are not a second
FNB evaluator. Future package layout is proposed `sdk/typescript/`, separate from
the existing private validation-only bindings package. Explicit Apache-2.0
package licensing and any necessary path-matrix update belong to that later PR;
this documentation's license does not automatically license a future SDK.

## 7. Versions, compatibility and supply chain

Keep four identifiers separate: schema `v0.1.0-preview.1`, transport wire `1.0`,
transport artifact `1.0.0-preview.1`, and independently versioned SDK. Proposed
first SDK artifact version `0.1.0-preview.1`, with candidate separate tag
`object-exchange-ts-sdk-v0.1.0-preview.1`; neither exists or is authorized now.
Package name/npm scope is unresolved until ownership and trademark checks,
not a publish instruction or invented official npm identity.

Supported versions are an explicit exact pair, not negotiated from mutable main.
Unsupported request pairs fail before network; server-side version Problem
Details remain decodable. Later versions require explicit metadata, generation
and matrix updates. SDK patches may fix tooling/HTTP ergonomics without moving
frozen upstream tags; any wire/semantic change requires appropriate upstream
governance/new immutable boundary first. Breaking SDK APIs require a new reviewed
preview version and migration note even before 1.0. No private Alpha guarantee,
cross-language compatibility claim, or third-party certification badge.

Target zero runtime npm dependencies. Reuse the pinned TypeScript `7.0.2`
validation baseline only after a later SDK compilation job explicitly proves
compatibility. A separate SDK package manifest/lock, exact generator/test/build
versions, integrity hashes, license inventory and SBOM are future gates.
Development dependency changes require review and clean locked installs; no
floating tool downloads, unpinned npx, lifecycle/postinstall hooks, or runtime
schema/problem URL retrieval. Builds and runtime tests must run without external
network after dependency provisioning; only the explicit loopback test sockets
are permitted. Record provenance for generated files and packaged bytes.

Repository checkout integration is not package-consumer acceptance. Before any
independent SDK release, require a clean pack/install consumer test, ESM/types
resolution, no undeclared imports or private paths, explicit package contents,
license/notice/SBOM, reproducible build+digest manifest, secret/dependency review,
security-supported exact toolchain, independent code/parser review, all matrix
rows pass and exact-head CI plus merged-main CI success. Select an actual merged
commit, create a separate signed/annotated immutable SDK tag, and verify it
remotely without changing earlier tags. npm publication needs separate explicit
authorization, verified namespace, credentials policy and provenance mechanism.
No npm publish, Go SDK, new transport tag, or release action in this planning PR.
